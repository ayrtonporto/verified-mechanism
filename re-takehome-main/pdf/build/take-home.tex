\vmsection{Background}

\begin{question}
Our autoresearch framework has LLM agents find theorems about the internal computations of
transformers and verify them in Lean 4. We believe we can get more from models when
they work together, and that unlocking this potential depends on finding the right way
for them to collaborate. This task recreates the
setting at a smaller scale with two lightweight models.
\end{question}

\noindent
Everything you need lives in one repository:

\begin{submitbox}
\href{https://github.com/VerifiedMechanisms/re-takehome}%
{\code{github.com/VerifiedMechanisms/re-takehome}}
\end{submitbox}

\noindent
\begin{bullets}
\item The kit contains ten development problems, a working single-model baseline,
scripts that set up Lean and Mathlib for you, and the one-page rules in
\href{https://github.com/VerifiedMechanisms/re-takehome/blob/main/RULES.md}%
{\code{RULES.md}}.
\item Your OpenRouter API key arrives in the same email as this PDF: a
\textbf{\$50 budget, on us}, for the two models named in the rules. 
\item Build with whatever you like, including your own chatbots and coding agents; at run time your system talks
only to the two fixed models through our key.
\end{bullets}
\newpage
\parthead{Part one}{Make two models prove things}

Each problem is a folder: \code{problem.md} states it in English,
\code{challenge.lean} states it formally, with \code{sorry} where the proof (and on some
problems a numeric answer) goes. Your system turns the folder into a Lean file the
compiler accepts, with our statement unchanged.

Build the coordination layer. Both models must take part in every scored attempt; how
you divide the work between them is the design problem. We would rather see a simple
design we can fully understand than a complicated one that scores marginally better;
if two systems score about the same, we prefer the simpler one.

Scoring is mechanical, on a private holdout with the dev set's format and grading:
about a dozen problems whose difficulty may vary, one point per correct problem, zero
for incorrect. A proof counts only if it passes the open-source Lean comparator
(\href{https://github.com/leanprover/comparator}{\code{leanprover/comparator}}):
it must compile against our pristine statement with no \code{sorry} and no axioms
beyond the standard three. A problem that spends more than \$1 scores zero even if
the proof is correct. We run your repository once per problem at 20 minutes and
\$1 each.


\parthead{Part two}{The eval science of collaboration}

Is your two-model system better than either model alone, and if so, where exactly does
one model fill the other's gaps? Run three conditions on the dev set or your own set of problems: \textbf{model A solo, model B
solo, and your collaboration}. 

Report per problem (which problems flipped between
conditions), while accounting for confounding factors as much as possible. Classify every failed attempt: wrong informal
solution; right solution but failed formalization; proof repair stuck; harness error.
Include at least two quoted transcript case studies, the holdout score you expect with a
sentence of reasoning, and a spend ledger.


\partend
